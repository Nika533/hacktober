## Native messaging (hoot-bridge, C-21)

- Chrome or Edge starts hoot-bridge with the extension origin as an argument. Only `allowedExtensionIds()` may call it; anything else gets `error: unauthorized`.
- hoot-bridge reads the per-launch token from `bridgeTokenPath()` (`%LOCALAPPDATA%\Hoot\bridge\token` on Windows). It connects to `bridgePipePath()` and starts `Hoot.exe --hidden` if nothing is listening. Its first pipe frame is `bridge.auth { token, origin }`; after that it relays frames unchanged.
- If there's no token, or the app never answers, the extension gets one `error { reqId: null, code: 'app_unavailable' }` and the port closes. The service worker treats a disconnect the same way.
- The app (C-20) writes the token with user-only permissions at start, and rejects a pipe client whose first frame isn't a valid `bridge.auth`.
- Packaging (C, #52): `hoot-bridge.cjs`, `register-native-host.cjs` and `hoot-bridge.cmd` ship in `resources/`, where the launcher finds `..\Hoot.exe`. The per-user NSIS installer registers the host for Chrome, Edge, Chromium and Brave (HKCU) and removes it on uninstall (not during an update). A packaged first run repairs a stale registration (`ensureNativeHost`). `scripts/smoke-packaged.mjs` (CI job `packaged`) checks this path end to end.

## Dev / e2e transport (d2)

`@hoot/bridge/testing` exports `createFakeLensServer({ port?, pairingCode?, delayMs?, settings?, profile? })`. It returns `{ url, pairingCode, backend, connections, close }`.

- Connect to `url` (`ws://127.0.0.1:<port>/?code=<pairing>`). A wrong code closes with 4401.
- Send one JSON bridge message per WebSocket **text** frame. There's no length prefix, because WebSocket frames already delimit messages.
- `backend` is a `FakeLensBackend` for assertions (`.events`, `.explained`) and pushes (`emitSettings`, `emitProfile`).
- The app's dev transport (`HOOT_DEV_BRIDGE=1`, C-20) speaks the same format.

## Fake Lens rules (for tests)

`createFakeLensBackend()` / `HOOT_FAKE_LENS=1`:

- A span containing `SKIP` is skipped; `ERROR` fails with code `busy`.
- An all-caps 2–6 letter span is expanded; one word is defined; a foreign-language span (`signals.foreignLanguage`) is translated; anything else is simplified.
- High risk, or a span over 40 words, renders as a gloss.
- `createFakeLensBackend({ delayMs })` honours `AbortSignal` (rewrite resolves `skipped: cancelled`). `.events` and `.explained` record calls.

## State subscription ordering (d1 implements, renderers rely on it)

- Main registers the window and takes the snapshot of the requested slices **in the same synchronous call** to `state:subscribe`. Every `state:patch` sent to that window afterwards is therefore never older than the snapshot.
- The invoke reply can arrive **after** such patches: a store flush can run before Electron sends the reply. **Renderers must hold any patches that arrive before the snapshot, apply the snapshot, then replay the held patches.** Applying the snapshot last would roll the state back.
- A delta is broadcast before any snapshot or patch that contains it (`mutate → chat:delta → patch`). Renderers ignore deltas until they hold a snapshot, because the snapshot already includes earlier ones.
- Each patch replaces whole slices. Renderers keep only the slices they subscribed to.
- Main also re-sends the subscribed slices once, on the next macrotask after the reply (#95), so a window converges even if it applied a stale snapshot. Holding early patches still matters: without it a stale snapshot shows for one tick.

## Feature plug-ins (main)

- Each feature folder exports `create<Feature>Service(deps)` and `create<Feature>Handlers(service)` from `apps/desktop/src/main/<feature>/index.ts` (chat, pins, capture, lens; the bridge server is `createBridgeServer`). d1 wires each one once in `AppContext`; feature owners never edit `context.ts`.
- Handlers register through `registerHandlerMap` (invoke channels, arguments validated). When a handler must know which window called, the factory returns `{ invoke, send }` with the sender first, registered with `registerSenderHandlerMap` / `registerSenderSendMap` (pins: a note window acts only on its own pin).
- Cross-feature calls go through `ctx.hooks`: `explain`, `showChatSurface`, `buddyAnchor`, `startCapture`, `takeClipboardSelection`, `setNotesVisible`, `openInReader`.

## Feature hand-offs

- **Capture → chat:** `addImageAttachment` saves `attachments/<id>.png` (`persistence.saveAttachment`) and appends to `chat.pendingAttachments`. `chat:send` takes every pending attachment and clears the list. `attachments:open` and `attachments:remove` belong to chat.
- **Clipboard → chat:** `clipboard:arm` snapshots the text; `takeClipboardSelection()` returns it once and clears the hint. Chat wraps it with `clipboardTextBlock` (capped at 8,000 characters). Nothing copied is sent unless the user armed it.
- **Explain more (Lens → chat):** `hooks.explain(message)` → `chat.startExplain(message)` stops a running answer, shows `text` and sends `sentText`.
- **Chat → buddy:** `onActivity` reports `thinking` / `talking` / `done` / `stopped` / `error`; d1 maps them to the owl's mood and `answerReady`.
- **Pins:** a note loads `note.html#<pinId>`. `pins:close`, `pins:openInHoot` and `pins:resize` act on the calling note's pin only. `pins:create` pins a finished answer of the open chat (a repeat shows the same note); `pins:createFromText` deduplicates on the exact text, which renders as Markdown.
- **Lens anywhere:** `settings.lensHotkey` (default `CommandOrControl+Alt+L`) reads the selection in the foreground app and opens the `anywhere` window (`anywhere.html`) under it. Main owns `AnywhereState` (`src/types/anywhere.ts`) and pushes it on `anywhere:update`; `anywhere:current`, `anywhere:act(AnywhereAction)`, `anywhere:close` and `anywhere:resize` act only for the bubble's own sender. Main builds the `LensContext` (`surface: 'app'`, `site: ''`) and every `LensEvent`.
- **Code link (VS Code):** its own pipe (`codeLinkPipePath`, `\\.\pipe\hoot-code-<user>`) and per-launch token (`codeLinkTokenPath`, `code-token` next to the bridge token). The extension opens with `code.hello`; the app then asks `code.snapshot.get` / `code.show` / `code.apply` / `code.reveal` / `code.clear` (one reply per `reqId`, all with timeouts) and the extension pushes `code.focus` and `code.applied`. When VS Code was in front, the live overlay (and any chat right after VS Code) appends `codeNote(snapshot, previous)` to what's sent instead of a screen grab; the model answers with `[[line: path:N, "label"]]` and `[[edit: path:N-M, "label"]]` + a code block. Main resolves them against that snapshot (edits carry the `expected` lines) and shows them in VS Code; `code:apply` / `code:reveal(messageId, tagIndex)` act on tag `tagIndex` of `parseCodeAnswer(text).tags`, `code:tagStates` reports each, `code:changed` says ask again. VS Code applies an edit only when the expected lines are still there (or found exactly once), as one undoable change. The live overlay decides per shape: the window under each new shape (`textAccess.windowAt`, Hoot's own windows looked through) picks VS Code, a browser or just the screen; what was in front at open (or at a restore from the owl) is the fallback. `Transcript.answerFooter` + `codeChangesFor(hoot.code, session)` (`@hoot/ui`) put the same Show / Apply under answers in the card, Studio and agents.
- **Agents:** extra chats, each a full `createChatService` on a store whose `chat` slice is the agent's own (`apps/desktop/src/main/agents`), published as the `agents` slice (streamed words at most every 50 ms). `agents:create` (card, Studio; resolves false when all `MAX_AGENTS` colours are out) opens an `agent.html#<id>` window; every other `agents:*` call comes from that window and acts on its agent (known by the sender): `send` / `stop` / `regenerate`, `minimize` (the renderer animates the card into the owl first, then main shrinks the window around `AGENT_OWL_AT`), `restore` (main grows it back, then the card animates out of the owl), `close` (stops the answer; the chat stays in `sessions`), and `dragStart` / `dragMove` / `dragEnd` for the free-floating owl. Agents get the code link through `code.forChat(source)` (their own reading of VS Code; their answers' tags show in VS Code and apply like the owl's).
- **Voice chat:** main owns it (`apps/desktop/src/main/voice`): Windows speech (System.Speech through a PowerShell helper, `HOOT_FAKE_VOICE=1` for the scripted fake) listens, the service sends what it heard with `chat.send(payload, { notes: [voiceNote(replies)] })`, reads the streaming answer aloud sentence by sentence (`speakableText` + `nextSpeech`) and listens again. Renderers only show the `voice` slice (`VoiceSlice`: `phase` off/starting/listening/thinking/speaking, `heard`, `level` 0–1, `problem`) and call `voice:start` (start, or cut Hoot off and listen), `voice:finish` (send now), `voice:stop` (end; the answer keeps streaming) and `voice:speak(messageId)` (read one answer). A message typed while it listens is answered aloud too. Settings: `voiceReplies`, `voiceRate` (`VOICE_RATES`).
- **Page link (browser extension):** additive messages on the Lens bridge, same protocol version. The extension sends `page.focus { focused, page }` (acked; `page: null` when its page link is off) and `page.ask { text, voice, snapshot }` from its popup (acked). The app asks `page.read { reqId }` (its own reqId); the extension answers `page.snapshot { reqId, snapshot }` (no reply). The app pushes `page.marks { tab, marks }` (empty clears). A chat right after the browser (it was focused last, within two minutes; VS Code wins when it was more recent) appends `pageNote(snapshot, previous)`; the model points with `[[find: "exact words", "label"]]`, which the extension highlights with the CSS Custom Highlight API. Private pages (`isDeniedHost`, a password field, a site rule `never`) are never read: their snapshot is `blocked` with no url, title or text. VS Code connections never speak it and ignore its pushes.
- **Lens requests:** `reqId`s must be unique across every caller (the extension through the bridge, the Reader over IPC), because the engine keeps one in-flight map: use `crypto.randomUUID()`. Lens settings changes reach `LensService.settingsChanged()` through the bridge server's `pushSettings`; finishing the cold start relaxes the profile at that moment.
